# Working on KIQR

Read `docs/PLAN.md` for the architecture and the decisions behind it, and `DESIGN.md` before touching anything in `web/`.

## Layout

- `crates/kiqr-core` — storage (files + git), events, crawler, markdown, profile model, providers, extraction/synthesis
- `crates/kiqr-daemon` — axum API, SSE, embedded web UI
- `crates/kiqr` — the `kiqr` binary: CLI + `kiqr daemon`
- `web/` — React + Vite + TypeScript; `npm run build` writes `web/dist`, which the daemon embeds
- `abilities/` — the ability folders that ship in the binary (compiled in with `include_str!`, installed to `~/.kiqr/abilities` on first run): `SKILL.md` instructions (`seemo-agent` is Seemo's tool guide, `make-images` the image process, `social-posts`, `marketing-plan` and the four profile prompts belong to core abilities) and the two shipped connections, `make-images/extension.yaml` (`kiqr-render`) and `browser/` (the real browser, service "A site behind a login", which X and Reddit run on; core, on from the start, its programs installed on the first connect). Everything else, including email over SMTP (`transport: smtp`) and the analytics readers, lives in the marketplace repository (`~/Projects/kiqr/marketplace`, github.com/kiqr/marketplace) and is installed from its `index.json`; format in `docs/abilities.md`
- `assets/fonts/` — Inter, bundled for the renderer
- Seemo: `crates/kiqr-core/src/tools.rs` (the built-in tool catalogue and groups), `abilities.rs` (ability contracts), `extensions.rs` (manifests, instructions frontmatter, the registry over `abilities/` folders, what ships and what is core), `secrets.rs` (`.env` files: KIQR's own keys), `vault.rs` (the Vault: machine-wide credentials, encrypted in `vault/vault.enc`, each scoped to its domains; values reach only the sign-in runner, never the API; `same_site` is the one host matcher), `access.rs` (`projects/<slug>/access.yaml`: which credentials a project's abilities may use), `conn.rs` (what a call goes through: the credentials granted for an ability's needs, `env_for` (credential values by the names the manifest maps them to, settings as `${NAME}`, KIQR's own keys), sessions, activity and the daily cap by credential, machine-wide, and the one readiness rule `Facts::state`), `channels.rs` (channels: owned or third-party, on a site (`domain`), with what Seemo may do there (`read`, `publish`, `reply`, `learn`; `Mode` off/ask/auto) and the `publisher` it posts as; spots named by a kind's target fields), `lists.rs` (lists of people to email: channels of kind `list`, `contacts.csv` never committed), `render.rs` (SVG via resvg, HTML via a browser), `media.rs` (media assets and their sources: the website built in, abilities with a `media:` block), `publishing.rs` (HTML for email and blog bodies, campaign tags on links), `agent.rs` (claude arguments, stream-json parsing, system prompt), `chat.rs`, `tasks.rs`, `marketing.rs` (the plan and campaigns), `metrics.rs` (snapshots, KPI bindings, windows), `memory.rs` (Seemo → Memory: the owner's rules and what Seemo learned, `memory.yaml`, the secret guard, the prompt lines), `sources.rs` (a manifest's source mapping into rows), `connect.rs` (the generic sign-in flows); the daemon's `agent.rs` (processes, transcripts, runs), `seemo.rs` (chat and task routes, approvals, the calendar, To do), `ext.rs` (the dynamic catalogue, the executor for http/command/mcp/smtp/builtin, instructions and secrets routes), `market.rs` (the one ability view: the list per project, the marketplace index, install, update, pause, remove), `marketing.rs` (plan and campaign routes, the cards behind them), `memory.rs` (the memory routes, `remember` with its note in the chat, the reflection after chat turns and task runs), `selfconf.rs` (`change_kiqr`: any change KIQR's pages make, checked and run on the yes; the map is `abilities/seemo-agent/SETTINGS.md`), `metrics_src.rs` (reading a source through its manifest's mapping, and KIQR's own publish count), `connect.rs` ("Sign in with …" from the Vault through kiqr.cloud: the callback makes or refreshes an oauth credential and its grants), `creds.rs` (credentials at work in a project: `pick` per call, what an ability still `missing`, `state`, token renewal, ability settings and their choices), `vault.rs` (the Vault routes, "Sign in with" a kiqr.cloud provider, favicons), `access.rs` (grants), `channels.rs` (the channel routes, `spot_of`: which channel a call means and so what Seemo may do there, `kind_for`, readiness and publisher candidates), `performance.rs` (the Performance view, refresh, the daily pull), `mcp_host.rs` (hosted MCP servers, one per credential and program, machine-wide), `programs.rs` (programs KIQR installs for official abilities, `requires`), `session.rs` (signing a login credential in on a hosted program, Needs a hand), `hand.rs` (a browser ability's acting tool as a goal: a model picks each action, KIQR types and checks the approved content and never sends twice; a route that worked is replayed next time), `hands.rs` (the live view: frames over the event stream, a person's clicks and keys back), `images.rs` (brand kit, rendering, the posts job's cards), `media.rs` (Library → Media: the sources, their items, the import), `publish.rs` (publishing to a channel as its publisher or to a new spot, approve / schedule / unpublish, the scheduled publishes, email), `lists.rs` (a list channel's people over HTTP and sends to a list, one message per person), `smtp.rs` (`transport: smtp`), `networks.rs` (networks as kinds, profile hosts, suggestions), `builtin.rs`, `scheduler.rs`; the CLI's `mcp.rs` (`kiqr mcp`, the MCP server, which reads the catalogue from the daemon)
- `seemo/PERSONA.md` — Seemo's standing instructions

## Rules

- No database. State is YAML/Markdown under `~/.kiqr`; the daemon is the only writer and commits after every logical change (`Store::commit`) with a readable message. Automated changes use the `[auto]` prefix. Never add git remotes or pushes.
- Secrets only in `.env`. Config files reference them by variable name.
- The CLI never touches files; it calls the daemon's API. Any new capability gets an API route first, then CLI and UI.
- Every state change emits an `EventKind`; the UI and `--watch` depend on it.
- UnblockingAPI is promoted only where pages could not be read: the crawl summary, its ability card, and one Seemo message per crawl. Nowhere else. It is an ability like the others, on when it has a key; there is no separate crawl switch.
- UI: follow `DESIGN.md`. Dark theme only, modelled on ContentWriter (`~/Projects/contentwriter`); when in doubt, do what ContentWriter does. Tokens in `web/src/tokens.css`; Inter throughout, JetBrains Mono for paths and numbers; teal for actions and live state, indigo for AI/learning, lime only for Seemo's mark. Icons from lucide-react; motion from `motion/react`. A field with a fixed set of values (a key's `options`, a target field's `enum`, the model list) is a select, never free text (`FieldInput`). Preview any UI change with the demo build (`npx vite build -c vite.demo.config.ts` in `web/`, open `dist-demo/index.html?demo`).
- Crawling: KIQR fetches pages itself; the model only reads fetched Markdown from the queue. Never make fetching wait on the model.
- Seemo acts only through KIQR's tools; never the provider's built-in tools (`--tools ""` stays; web reading is `read_url` over our fetcher, not WebFetch). A new capability is a route, then a tool, then the UI; one that a connection could provide is an ability contract in `abilities.rs` plus a manifest, yaml first and Rust only when yaml cannot express it. Anything with side effects a person should see first goes through an approval (`create_task`, `change_config`, `save_ability`, `create_channel`, `publish_asset`, `send_email`, an ability's acting tool); publishing or acting asks unless the channel allows that role on its own (`publish: auto`, `reply: auto`), is refused where it is `off`, and even on its own the card is put in the chat as the record. A spot that is no channel always asks, and the yes adds it as one; an acting call with no channel always asks. What Seemo makes is approved whole: an asset shows in the chat as it will look, image included, and the user approves it there, in the Library or on Seemo → To do; images are never approved on their own. An asset's status is derived, never set: Draft until approved for a channel (Ready), Scheduled with a publish time, Published when it went out, Archived when put away; the user's only direct moves are unpublish, archive and bring back. Everything Seemo writes comes with a featured image (a post's image, an article's cover, an email's header), all on brand; a type says so in its `TYPE.yaml` (`image: always | usually | none`) and the image lands in the role the type names. The system prompt stays small (the brief and the list of abilities with instructions, not the profile: argv is capped at 128 KiB).
- Modular by default. The code names no app, platform or service except UnblockingAPI and the AI model providers. Core is the machinery with no alternative (contracts, transports, generic sign-in flows, approvals, storage, the scheduler, the crawler, the profile pipeline, the plan); anything that could be replaced by something else is an ability in the marketplace, and its specifics (hosts, requests, how it signs in, how a response becomes rows) live in its own manifest. When yaml cannot express what an ability needs, add a generic mechanism to core, never Rust for one service, and never dispatch on a manifest's id. Core may ship a default behind a contract (the renderer behind `image`) as long as an ability can take its place. What does not follow this yet is listed in `docs/PLAN.md` ("Modular by default").
- Three nouns for the user: the **Vault** holds credentials, **Channels** are where, **abilities** are what (decided 2026-11-02; replaces accounts and the Audience). The **Vault** (Setup → Vault) is machine-wide: logins, API keys, signed-in apps (one click through kiqr.cloud, promoted first) and mail servers, each a set of fields scoped to one or more domains (the first is its icon, its favicon); it knows nothing about abilities, channels or projects, and secret values never come back out. **Channels** (Marketing → Channels) are everywhere the business's people are, owned (its X profile, its company page, its blog, its mailing lists) or third-party (a subreddit, a forum, a Slack channel); each holds what Seemo may do there (read on/off, publish and reply off / ask / auto, learn for owned ones) and its **publisher**, who Seemo posts as; a channel needs nothing to exist and shows the one thing missing (no ability for its site, no publisher, the publisher not working) with its fix. A website is a channel too (kind `website`): it picks the ability it is published through (a repository that builds it, a blog engine), never matched by domain, and holds that ability's target fields (its repository). Publishing goes to a channel; Seemo acts on its own only where the channel says auto, and anywhere else asks, the yes adding the spot as a channel. **Abilities** (Setup → Abilities) are what Seemo knows how to do; they declare the `hosts` they work on and the credentials they would like, never own one: a project grants a credential to an ability (`access.yaml`), suggested by host, and choosing a channel's publisher is the only implicit grant. Matching is always host ↔ domain (`vault::same_site`): a credential's values go only to its own domains. Core abilities switch off but never leave; every installed ability is visible, switchable and updatable; nothing but writing, the renderer, web reading and the browser is on by default. What the project picks once for an ability (a GA4 property) is its setting, kept in the project. There is no "audience", "place", "connection" or "skill" in the UI. Seemo sees tools named after ability contracts and reads instructions with `read_instructions`; the code has extensions, transports (http, command, mcp, builtin) and kinds (where content goes out, declared by manifests). Only KIQR's own keys (model providers, UnblockingAPI, kiqr.cloud) live in `.env`, set by name through the daemon. Values are never shown or sent to the model.
- Seemo writes in first person, plainly, no emoji or exclamation marks; it never claims to have done something it has not.
- Keep `docs/PLAN.md` current when a decision changes.

## Build and test

```sh
cargo build
cd web && npm ci && npm run build
KIQR_HOME=/tmp/kiqr-dev ./target/debug/kiqr daemon   # throwaway home
./target/debug/kiqr project add http://127.0.0.1:8099/ --watch
```

A quick local site for crawl tests: `python3 -m http.server 8099` in a folder of HTML files.
