# KIQR — architecture and plan

KIQR is a self-hosted marketing agent. You give it a website; it crawls it, builds a business profile with evidence for every fact, and from then on Seemo, the CMO persona, plans and runs marketing with you. This document is the design the code follows and the roadmap after the MVP.

## Decisions

- **Open source, no account required.** Everything in this repo runs on the user's machine (or in Docker) with their own Claude/Codex subscription or API key. kiqr.cloud adds optional pro features; it never gates the core.
- **Rust.** One binary, `kiqr`: CLI and daemon (`kiqr daemon`). The web UI (React + Vite) is built to `web/dist` and embedded in the binary.
- **Files, not a database.** `~/.kiqr` (or `/data` in Docker) holds YAML and Markdown under a local git repo. The daemon is the single writer and commits after every change with a readable message; automated commits start with `[auto]`. There are no remotes and no pushes; a user who wants a backup adds a remote and pushes with plain git. Raw fetches live in `projects/<slug>/cache/` and are ignored.
- **Secrets in `.kiqr/.env`**, mode 0600, ignored by git. Config files reference secrets by variable name only.
- **Built-in fetcher first; UnblockingAPI on escalation.** Pages that return 401/403/429/503, show a bot challenge or are empty JavaScript shells are retried through UnblockingAPI when a key is present. Without a key they are reported as unreadable, and UnblockingAPI is mentioned exactly there: in the crawl summary, in Settings, and once by Seemo.
- **Providers.** `provider/model` strings per task (`extract`, `synthesize`, `chat`): `anthropic/…`, `openai/…` over HTTP with keys; `claude-cli/…`, `codex-cli/…` through the local CLIs with the user's login. Docker runs on API keys or `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`.
- **`web/dist` is committed** so `cargo install --git` works without Node. Rebuild it (`npm run build`) in the same commit as any UI change; `scripts/release.sh` also rebuilds it for every release, and the release workflow builds it fresh before compiling.
- **Releases are prebuilt, semver, cut by a tag.** `scripts/release.sh <patch|minor|major|rc|X.Y.Z>` bumps `[workspace.package] version` (the one version), writes the CHANGELOG entry ("Unreleased", or the commits since the last tag), commits `Release vX.Y.Z`, tags and pushes; `.github/workflows/release.yml` checks the tag matches `Cargo.toml`, builds six targets on native runners (`x86_64`/`aarch64` Linux musl, macOS, Windows MSVC) and publishes a GitHub Release with `kiqr-vX.Y.Z-<target>.tar.gz` (`.zip` on Windows), a version-less copy of each for `/releases/latest/download/`, `SHA256SUMS` and `latest.json` (`version`, `notes_url`, `assets.<target>.{url, sha256}`). `-rc.N` tags are pre-releases, which `/releases/latest` skips. Before 1.0 a minor release may change the home layout or the API; a patch only fixes. `ci.yml` builds and tests Linux, macOS and Windows on every push to main.
- **Installing is downloading; running the installer again updates.** `install.sh` (Linux, macOS) and `install.ps1` (Windows) pick the archive for the machine (an arm64 Mac under Rosetta gets arm64), check its SHA-256 against `SHA256SUMS`, swap the binary by rename, and register the daemon (systemd user unit, launchd agent, or a Task Scheduler task at logon), restarting it when the version changed. `KIQR_VERSION` pins a release, `KIQR_FROM_SOURCE=1` (or a platform without a build) falls back to `cargo install`. kiqr.dev redirects `/install.sh` and `/install.ps1` to the files on `main`, so the site never serves a stale copy.
- **KIQR updates itself, when asked.** The daemon reads `latest.json` (`KIQR_UPDATE_URL` overrides; it is KIQR's own release feed, not a service an ability could replace) 20 s after start and every 6 h (`KIQR_UPDATE_CHECK=0` turns it off), compares versions with semver and emits `update_available` once per new version; `/api/health` carries `update`, Settings shows "vX available" with an Update button, `kiqr status` says so and `kiqr update` installs it. `POST /api/update` refuses while Seemo is working or a job runs, downloads the archive for the build's own target (`build.rs` records it; glibc and MinGW builds take the musl and MSVC archives), checks the SHA-256, runs the new binary's `--version`, renames it over the old one (`self-replace` on Windows), emits `updated` and restarts: `exec` in place on Unix, so systemd and launchd see the same process, and on Windows a second instance of the scheduled task (or a detached process without one), which waits for the port. It installs on its own only when the user switched `updates.auto` on (Settings → General → Updates, `kiqr update --auto on`, or `KIQR_AUTO_UPDATE=1` at install): then the background check installs a new version when no turn or job runs, retrying every 5 minutes while one does. It refuses with the reason in Docker (`KIQR_IN_DOCKER`), in a development build, for a Cargo install and when the binary's folder is not writable.
- **An anonymous usage ping, on unless switched off.** So we know how many install KIQR, run it, are live now and bounce, how many sign in to kiqr.cloud and which abilities they install, the daemon (`telemetry.rs`) posts to `{cloud.url}/api/v1/ping` 30 s after start, every 15 min and right after `extension_installed`. It sends a random id made on the first ping (`telemetry.id` in `config.yaml`; a config saved without it keeps it), the version, OS, architecture, Docker yes/no, kiqr.cloud signed in yes/no, the ids of installed abilities that the catalogue (shipped or the marketplace index) lists, and only a count of the others. No hostname, project, URL, key or email. `GET /api/telemetry` shows the exact body; `PUT /api/telemetry`, `kiqr telemetry on|off` and Settings → General → Usage stats switch it; `KIQR_TELEMETRY=0` and `DO_NOT_TRACK=1` override. The installer says so in one line. kiqr.cloud keeps one row per id plus the abilities seen, no IP, and shows the numbers on `/admin`.
- **The daemon is a per-user service; `kiqr start | stop | restart | status` drive it.** The installer registers a systemd user unit (`kiqr.service`), a launchd agent (`dev.kiqr.daemon`, KeepAlive, so stopping it means unloading it) or a Task Scheduler task ("KIQR daemon", at logon, parallel instances allowed), carrying `KIQR_HOME` when it was set at install. The CLI finds which one exists (`crates/kiqr/src/service.rs`) and goes through it; with none (`KIQR_NO_SERVICE=1`, a Linux without systemd) `kiqr start` runs `kiqr daemon` detached, logging to `<home>/daemon.log`, and `kiqr stop` ends the process by the `pid` in `/api/health`, as it does for a daemon some other way started. These are the CLI's one exception to talking only to the API: a stopped daemon has none. A self-update on Windows restarts through the task (`schtasks /Run`, then the old instance exits), so the task keeps owning the daemon.
- **Port 4040, set in Settings → Network, applied by a restart.** The daemon listens on `daemon.host`/`daemon.port` in config.yaml (default `127.0.0.1:4040`; `KIQR_HOST`/`KIQR_PORT` override it, and Settings then shows the address as set by the environment). Homes still on 7777, the default before 0.2 that nothing could change, move to 4040 once on start (`[auto]` commit). Saving a new address, in Settings or through Seemo's `change_config`, checks it (an IP address, a free port) and restarts the daemon there with the same arguments as soon as no chat turn, task run or crawl is running (`restart_when_idle`, the same in-place restart the updater uses); `config_changed` with `restart` tells every open page, which waits until the new address answers and moves there. Sign-ins don't care: kiqr.cloud accepts loopback callbacks on any port (RFC 8252).
- **Windows is a first-class target.** Programs are found and started through `kiqr_core::process` (PATHEXT, so npm's `.cmd` shims like `claude` resolve; the environment a child keeps includes `SystemRoot` and friends), a turn is stopped with `taskkill` instead of SIGINT, and the home falls back to `USERPROFILE`. `git` is still a runtime requirement on every platform.
- **Crawling is two independent stages.** KIQR fetches pages itself (reqwest, or UnblockingAPI on escalation), `concurrency` at a time (default 5, max 10). Every fetched page is queued for the model, which reads `ai_concurrency` pages at a time (default 3). A slow model never slows the fetcher. Both are per-project settings and can be set per run.
- **Demo mode.** `?demo` (or `window.__KIQR_DEMO__`) replays a scripted crawl into the real screens without a daemon; `web/vite.demo.config.ts` builds one self-contained HTML file for previews and the site.
- **SSE, not WebSockets.** All state changes flow daemon → client as events; actions are POSTs. `kiqr crawl --watch` prints the same stream.
- **A project is built before it is used.** Its first build (crawl, the model reading, the profile and the brief) is one state, folded from the crawl's events by `crates/kiqr-daemon/src/build.rs`: stage (`new`, `crawling`, `reading`, `writing`, `ready`, `failed`), one overall percentage that never goes back (fetching 30, reading 35, writing 35), the seconds left at each stage's own measured pace, and a problem in plain words when it can't finish (no model, an unreachable site, writing failed). It is `build` on the project, `GET …/build`, and `build_progress` (at most once a second) and `build_stage` events. A brief means ready for good: crawling again never locks a project. Until ready, `require_ready` refuses plans, campaigns, tasks and posts with 409, Seemo's prompt says it is still reading and not to propose or make anything, and the UI keeps the project in the welcome flow (DESIGN.md). While it reads, Seemo asks the owner four skippable questions; the answers (`projects/<slug>/intake.yaml`, `PUT …/intake`, `intake_saved`) go into the brief prompt as `owner_says` (what comes first, never as evidence) and into Seemo's prompt.
- **Crawls replay.** The daemon logs every event of a project's latest crawl job (crawl plus synthesis) in memory, and on finish keeps it in `cache/crawl-log.jsonl`. `/api/events?project=…&replay=1` sends that log first (frames marked `"replay": true`), then `replay_done` with `running`, then live events, with no gap between them. The crawl screen and `kiqr crawl --watch` use it, so leaving the page or joining mid-crawl shows the whole crawl.
- **Only the business's own pages.** KIQR crawls the site and nothing else. Links with `target="_blank"` or `rel` nofollow, noopener or sponsored are never followed, even internal ones: that is how sites mark outbound and affiliate links. Redirects are followed within the site (http→https, www, moved pages) and never to another website: a link that redirects away (`/till/…`, `/go/…`) is skipped (`page_skipped`) without fetching the other site's page, and after three such redirects under one path the rest of that path is skipped without a request. Two links that land on the same page read it once. If the project's own start URL redirects away, Seemo says so. Pages cached by older crawls that left the site are ignored by the profile, the brief and the brand, and before synthesis any evidence from them is removed from the profile (fields that rested only on it are dropped, locked fields kept). Brand imagery comes only from the business's own hosts: its domain and subdomains, and the hosts its own logo, icon and share image live on (a shop platform's CDN); resized copies of one picture count once. Social profiles count as the business's own only when its JSON-LD Organization lists them (`sameAs`), when the handle is its name or domain, or when they sit in the header or footer of at least half its pages; JSON-LD inside products (a product's brand or seller) and organisations with another website are ignored.
- **Brands are saved, not rebuilt per view.** Building a brand reads every cached page (seconds), so it happens once: at the end of a crawl, on a project's first brand request, and at daemon start for projects without one. Each saved brand records the collection `rules` version that built it; when the rules change (`brand::RULES`), outdated brands are rebuilt from the cache the same way.
- **Live page limit.** A running crawl's page limit can be changed while it fetches (`PUT /api/projects/{slug}/crawl/limit`, the crawl screen's "Raise the limit" dialog, `kiqr crawl <slug> --max-pages N`). The crawler checks the limit before each fetch, and pages over the old limit stay queued, so a raise continues straight away. Once fetching has ended the limit applies from the next crawl; the response says which (`live`). The limit is saved to the project either way, and the change is the `crawl_limit_changed` event.
- **One job per project.** Starting a crawl, synthesis or brief claims the project's slot in one step; a second request gets 409. A crawl ends by rebuilding the profile, so it doesn't overlap a profile job either. `GET /api/projects/{slug}` lists running `jobs`, and `job_finished` says when one ends. The UI shows a running crawl instead of starting another; `kiqr crawl --watch` follows it.
- **Assets, in a Library.** What users make with Seemo (articles, posts, Reddit replies, images, memes, videos, songs, ad campaigns, and kinds nobody has defined yet) are assets. A type is data, not code: `asset-types/<type>/TYPE.yaml` names it, picks a lucide icon, lists the files it holds, how to preview it (article, post, image, video, audio, campaign or files) and whether its assets carry an image by default (`image: always | usually | none`: posts, articles and emails always do). Everything Seemo writes comes with a featured image; Seemo reads the type and the image lands in the role the type names (`cover`, `media`). Built-in types ship in `asset-types/` and are installed like the built-in instructions; users and Seemo add more (`POST /api/asset-types`), and the sidebar grows an item for each type that has assets (archived ones aside: they show only under Archive). An asset is a folder, `projects/<slug>/assets/<type>/<id>/`: `asset.yaml` (type, title, status draft/ready/scheduled/published/archived, tags, who made it: `user`, `task:<id>` or `chat:<id>`, what it was made from, its files with size and sha256, and where it was published) plus its files.
- **Seemo's first assets.** The getting-started guide (on To do, which is "Getting started" until every step is done or skipped; the Library shows what has been made) ends with three optional steps (skippable, remembered in the browser): generate 3 social media posts, connect where you publish, and put Seemo on the calendar. Posts are written by the chat model with the `social-posts` instructions from the brief and the brand's own social networks, saved as draft `post` assets made by `seemo` (`kiqr assets generate <slug>`).
- **Generated assets stay out of git.** `projects/*/assets/` is ignored (videos and audio would bloat the history), so asset changes emit `asset_saved`/`asset_deleted` but are not committed. The library is read from the folders. Backups to S3 come later. Asset types are configuration and are committed.
- **Seemo chat is Claude Code with KIQR's tools.** Each chat turn and each task run is one `claude -p` process (stream-json, `--tools ""`, `--strict-mcp-config`, no `--bare` so the user's subscription login works) whose only tools come from `kiqr mcp`: the same binary serving KIQR's API over MCP on stdio, told the project, the chat or run, and the allowed tool groups through its environment. The tool catalogue lives once in `kiqr-core::tools` (groups `read`, `write_profile`, `write_assets`, `jobs`, `tasks`, `config`); each tool is one request to the daemon, so the MCP process never touches files. A chat keeps the provider's session id and resumes it every turn; our own transcript (`chats/<id>/messages.jsonl`, committed per turn) is the record, and when the provider has forgotten the session a new one starts from that transcript. The system prompt is the persona, the `seemo-agent` guide, where we are (project, local time and timezone, running jobs, tasks) and the brief as compact JSON; never the whole profile, which is over Linux's 128 KiB argument limit and is a tool call away. The chat model must be `claude-cli/…` for now; Codex and HTTP providers get their own tool loops later. **No built-in tools, ever:** Claude Code's Bash, Read, Write, WebFetch and WebSearch stay off (`--tools ""`), whatever the provider. Every capability Seemo gets is one of ours, so it behaves the same on every provider, is confined to what KIQR knows how to do, and shows up as a step the user can read. Reading the web is `read_url` (group `web`), which goes through KIQR's own fetcher with the UnblockingAPI fallback, not WebFetch; images, search and the like will be KIQR tools in the same way. The `assets/generate` job stays as the provider-agnostic way to write posts (`kiqr assets generate`); the `social-posts` instructions give every post an image idea (headline, support line, style), with the title over the first sentence as the fallback, and the daemon renders it as a branded card with the built-in renderer, so every post has an image on every provider.
- **Approvals.** Two tools ask the user first: `create_task` and `change_config`. The tool opens an approval (`POST …/approvals`), the chat gets a card, the tool polls until the person approves or declines in the UI (or 15 minutes pass), and Seemo finishes its turn knowing the outcome. Approving a config change saves `config.yaml`, commits, swaps the daemon's cached config and emits `config_changed`; host and port apply after a restart and the card says so. Secrets can never be set this way.
- **Seemo is the automation.** A task is a plain-language instruction, a schedule (once, or an RRULE with an IANA timezone: "weekdays at 10:00", "every day in December until the 24th") and the tool groups its runs may use (never `tasks` or `config`: those need a person). Seemo proposes tasks from chat; the user confirms once on the card, which shows the schedule in words and the next three occurrences; "do it now" is a one-off task that runs on approval. Each run is a headless Seemo session, recorded in `tasks/<id>/runs/<ts>.yaml` (steps, assets made, summary, cost); runs hold `task:<id>` in the job set, not the crawl slot, so they may overlap a crawl. The scheduler ticks every 30 s; runs due while the daemon was down execute once if under an hour late, otherwise they are recorded as missed. A one-off task made in a chat reports back there: the daemon adds a note and Seemo writes one message about the result. Scheduled runs only update their card and say one line as `seemo_says`.
- **Two words for the user, one folder underneath.** The user sees an **ability** (something Seemo can do: write, crawl a site into a business profile, read the web, create images with the built-in renderer or with fal.ai, send email, publish to WordPress, write product update posts the way we do) and a **channel** (where a project's content goes out: an email address, a blog, an account). An ability may carry instructions (plain words Seemo reads before that kind of work), a connection (a key, a program, an MCP server), or both; the user never has to know which, the card says what is included. Skills are gone as a word: a recipe written on the Abilities page is an ability like any other, listed in the same place, switched the same way, shareable through the same marketplace. Seemo sees only tools, named after ability contracts (`create_image`, `send_email`), whatever installed ability is behind them (`config.abilities` picks one when several are ready, else the built-in one, else the only ready one), plus the abilities with instructions in its prompt and `read_instructions` to read them. The code has one package, the **extension** (a folder with a manifest), and a **transport** (built-in Rust, declarative HTTP, a local command, an MCP server the daemon hosts; a cloud relay later). The words tool, MCP, API, plugin, gateway, connection and extension appear only under Advanced and in `docs/abilities.md`. The daemon is the one gateway for every transport: secrets, host allowlists, approvals and the audit trail live in one place.
- **One page for abilities, per project; installed once, configured per project; core ones switch off but never leave.** Setup → Abilities is the one page: what Seemo can do here (Yours, From the marketplace, Built in) as rows with the state, what each includes (instructions, key or account, program, MCP server, publishes) and a switch for this project; "Teach Seemo something" (a name as an action, when it applies, the instructions, this project or every project); the marketplace below (search, shelves, vendor filter, cards with install); Advanced for folders, git URLs, broken folders and Seemo's own guide. Settings has no Abilities tab; older links land on the first project's page. Every ability opens in its own modal: Overview (summary, when Seemo uses it, what is included with the details, where it came from), Instructions (the text; edit a copy for this project or for every project; drop a copy; back to the shipped text), Accounts, or Channels for one that publishes (this project's accounts of it, each with its own keys, the default starred; which ability is preferred for a contract when several are ready), and a footer with one switch (this project), Update and Remove. Until 2026-10-26 the footer had a second switch for every project, and keys could be machine-wide; see "Abilities are code; accounts belong to the project". The index is `config.marketplace.url` on kiqr.cloud, fetched and cached for an hour, with the manifests KIQR ships as the offline list; a community ability is a git repository the index points at, instructions only or with a manifest. Install is for the machine, once: it clones that repository (or writes a shipped manifest) into `~/.kiqr/abilities/<id>` with no keys, and the project adds its accounts next; Update pulls; Remove deletes the folder. Core abilities are code (`CORE_ABILITIES`: write, crawl a website into a business profile, read the web, read blocked pages with UnblockingAPI, write social media posts, run tasks on a schedule) plus the renderer's folder; each may own shipped instruction files (the profile pipeline's four prompts belong to the crawl ability; `social-posts` to the posts ability) that the user edits as copies, and `seemo-agent` is Seemo's own guide under Advanced. They sit in the same list, always installed, never removed; a core ability can be off for every project in `config.core_off`; otherwise the switch is a project's own, `abilities_off` in `project.yaml` (an installed folder's old `.off` marker became that, once). Off takes the tools with it (writing: `create_asset`; reading the web: `read_url`; tasks: `create_task` and the scheduler; crawling and the posts job refuse; UnblockingAPI stops escalating), drops the ability from the prompt, and makes `read_instructions` refuse. An ability with keys cannot be switched on before the project has an account of it with all of them. Keys live on the account (`projects/<slug>/connections/<id>/.env`), set from the Accounts or Channels tab or the Channels page. Abilities are named as actions ("Create images with fal.ai", "Post to X with Chrome"), never as plugins, and each shows its vendor: the GitHub user or organisation behind its repository, `kiqr` for KIQR's own, `you` for yours. The marketplace itself is a git repository (`kiqr/marketplace`: `index.json` plus one folder per ability KIQR publishes). An installed folder is committed to `~/.kiqr` with `.source` naming its repository and path. There is no separate escalation switch: blocked pages go to UnblockingAPI when that ability is on and has a key. Older homes: every shipped ability that was never set up went back to the marketplace on first start, and `skills/` folders were moved to `abilities/` once, committed.
- **Images are rendered, not generated, by default.** Claude has no image model; claude.ai writes SVG or HTML and renders it, and so does KIQR. `brand_kit` gives Seemo the brand's colours with roles, the fonts as they will render here, the logo and icon as local files, and preset sizes; `create_image` through the built-in connection `kiqr-render` renders SVG with resvg (system fonts plus a bundled Inter, `assets/fonts/`) and HTML with a Chromium, Chrome, Brave or Edge found on the machine, headless with the network off. Nothing to install, nothing to pay. A generator (fal.ai, OpenAI images, anything with a manifest) takes over the same tool with a `prompt` when the user picks it under Settings → Models. The renderer's instructions (`make-images`) hold the process and five templates. Images land on an asset in the role its type names (a post's `media`, an article's `cover`) and show in the chat step, the library card and the asset page; a card without an image takes the brand's accent, and a post is previewed as a feed card (modal from the grid, full page by link). Built-in instructions follow each release unless the user edited them (`.builtin` beside the file remembers what was installed; an older copy is kept as `SKILL.previous.md`). **Media is never approved on its own.** What Seemo makes through a media ability lands on the asset at once, in a chat as in a task run; the asset is what the user approves (next decision). An earlier version kept each image aside behind a `media` card and asked first; it doubled every post into two questions and a run that waited per image produced posts without images, so it went.
- **Status is derived, approval is the user's, and everything waiting sits in one place.** An asset carries facts, not a status: `channel` (the user approved it for that channel), `publish_at` (the daemon publishes it then), `publications` (where it went) and `archived`. `Asset::derived_status` turns them into Draft → Ready → Scheduled → Published, or Archived, on every load and save; nobody, Seemo included, sets the status (older files that said `status: archived` are read as `archived: true`). Approving a draft means picking the channel: one fitting channel is one button ("Approve for Facebook page"), several are a picker, none is "Add a channel first". Then Publish now or Schedule (a time; the scheduler publishes it on the first tick after, and a failure stays on the asset as `publish_error` with Seemo saying so). The user's only moves backwards are Unpublish (KIQR stops counting it; nothing is taken down and the record says so), Archive and Bring back. `publish_asset` takes `at` for Seemo to propose a scheduled publish behind the same card. The same block of actions sits under a post in the chat (the asset shows there as it will look, image included, live while the image lands), in the Library's modal and page, and on **Seemo → To do**: open approvals from every chat (answerable there), drafts to approve, what is approved but not sent, publishes coming up, failed publishes; the sidebar carries the count of approvals, drafts and failures. Scheduled publishes are on the calendar beside task runs.
- **Seemo owns a plan, and it is short.** `marketing/plan.yaml` holds a period, a summary, two to four objectives (an outcome as the title, a `why` from the brief, one KPI from a fixed vocabulary, a target with its unit when something can measure it, a date) and the channels in play; `campaigns/<id>/` holds initiatives towards an objective, with assets joining through `source.campaign` and tasks through `campaign`. Seemo proposes the plan on a card (`propose_plan`, approval kind `plan`; a new proposal replaces the old plan as the next version and says why) and campaigns the same way (`create_campaign`, `update_campaign`, kind `campaign`); the user edits either by hand on Your business → Plan. The system prompt carries the period and one line per active objective, or a line saying there is no plan yet and that Seemo should propose one when strategy comes up. The `marketing` core ability carries the instructions for building a plan; the `marketing` tool group is what a task must be allowed to change it.
- **Numbers come from connections, are kept as snapshots, and sit against the plan.** A connection may declare `sources` (`traffic`, `search`, `conversions`, `ranks`, `mentions`); each declared source carries its own requests and a mapping from the answer into rows (`kiqr-core/src/sources.rs`: an array pointer, the day, metrics, breakdowns, a filtered sum or a ratio as derived metrics), run through the same executor as any call, so the marketplace's Google Analytics 4, Search Console (a service account through `connect: service_account`) and Plausible readers are yaml and KIQR's code knows none of them. The daemon reads each source once a day after 05:00 local, and on Refresh, into `projects/<slug>/metrics/<source>/<YYYY-MM-DD>.yaml`: 30 days of day totals plus breakdowns (channel, query, page, event); `kiqr` is a source of its own, what went out per day and channel. Nothing in the UI or the prompt waits on an API. A plan KPI maps to one (source, metric): `organic_traffic` → traffic.organic_sessions, `signups` and `qualified_leads` → conversions.key_events, `rank_positions` → ranks.average_position, `published` → kiqr.published; the Performance page shows each objective's KPI against its target over 30 days first, then the sources in one tabbed panel with every metric with the last 7 days against the 7 before and a 30-day line, the top queries and pages, and which connection read what and when; the Plan page shows "now x of target" on each objective. `read_metrics` gives Seemo the same view. Links to the business's own site in anything KIQR publishes carry `utm_source=<channel kind>`, `utm_medium=kiqr` and `utm_campaign=<campaign>`, so GA4's rows line up with campaigns. Rankzon joins as a source when it has an API; `config.abilities["source:<name>"]` picks the connection when two read the same source.
- **Core ships in the binary; everything else lives in the marketplace.** What KIQR cannot do without (the core abilities in code and their instruction folders, the built-in renderer in `make-images`) is compiled in and installed on first run. Every other ability, including email over SMTP (`transport: smtp`) and the analytics readers (yaml source mappings), is a folder in the marketplace repository and installs from its `index.json` (`config.marketplace.url`, default github.com/kiqr/marketplace). One copy of each manifest, nothing drifting. The index is cached for an hour on disk, but a daemon start and every opening of the app drop the cache and read it again in the background (`POST /api/abilities/refresh-index`, then `marketplace_refreshed`), and avatar URLs carry the fetch time as a version so a changed mark is refetched by the browser. When the index cannot be fetched the marketplace says so and lists only what ships; a folder or git URL still installs under Advanced. Decided 2026-10-25.
- **Teaching Seemo is adding an ability.** `abilities/<id>/` (the machine's, or `projects/<slug>/abilities/` for one project, which wins on a clash) holds `SKILL.md` (instructions: frontmatter with the action name and when it applies, then the text) and/or `extension.yaml`. The system prompt lists every ability that has instructions and is on, as `id — name: when` (capped at 3 KB), so Seemo reads the right one with `read_instructions` before acting; `list_abilities` says what is on and set up. "Teach Seemo something" is a form (what Seemo should be able to do, when, the instructions with three starter shapes, this project or every project) for people who will never open a file; Seemo can offer to keep a way of working the same way (`save_ability`, behind a card). Built-in `extension.yaml` files follow each release; built-in instructions follow too unless edited.
- **Connections run through the daemon, never past it.** A manifest declares what it needs (`auth`, keys by variable name, set on one of a project's accounts of the ability and written to that account's `.env` by the daemon, never read back), the hosts it may call (enforced, redirects not followed), what it provides (`provides.<ability>` with a request, a command or an MCP tool, and a `result` map that turns a URL or base64 into a file on the asset) and any tools of its own (offered under the connection's own group, `ext:<id>`). `${ENV}` is filled by the daemon at call time; `{{arg}}` from the tool's arguments; `map` rewrites an argument first. `transport: command` runs a program with the arguments on stdin and reads stdout, so a user's own script becomes a tool without the model getting a shell. `transport: mcp` servers are started on first use, kept alive, restarted once, killed with the daemon; `expose` offers their tools raw. The catalogue is dynamic: `GET /api/tools?project=` merges built-ins, the abilities with a ready connection and the connections' own tools, and `kiqr mcp` reads it from the daemon, so a new connection needs no rebuild. Format and examples: `docs/abilities.md`.
- **Channels publish with a yes, until the user says otherwise.** A channel (`projects/<slug>/connections/<id>/`, committed but for its `.env`) is one account of an ability that declares channel kinds, with its own keys, plus a kind and a destination; a project has as many as it wants. `publish_asset`, `send_email` and `create_channel` are approval tools: the card shows what goes where, with the subject, the first lines and the files, and only a yes sends. Each channel has a switch, "Seemo may publish here on its own" (`asks_first: false`, `kiqr trust`), for when the user has seen enough to trust it: a publish Seemo proposes then goes through at once, the same card lands in the chat already resolved ("Published by Seemo", or the failure), and a task still needs `publish` among its allowed groups. A task run that reaches one gets the card in the task's follow-up chat (made if needed) and waits; `publish` is not in a task's default groups and must be allowed when the task is created. The asset becomes `published` with a `Publication` (channel, account, url), the channel counts it, `asset_published` fires and the commit says where it went. Email is the built-in kind (`kiqr-smtp`, lettre: STARTTLS, TLS or plain for a local relay; Gmail with an app password), as both plain text and HTML with the asset's media attached. Other kinds come from manifests: the publish tool gets the title, Markdown, HTML, summary, tags and the destination fields.

- **Steps and uploads in the manifest** (roadmap 16, decided 2026-10-26). Publishing with media takes several calls (register an upload, send the bytes, create the post with the id), and media endpoints want a form, multipart or the file itself as the body, not JSON. A tool (or a provided ability) may therefore declare `steps` instead of one `request`: each step is a request with a `name`, `save` (pointers into its answer, used later as `{{name.var}}`), `when` (skipped when empty) and `for_each` (once per file of the asset, or per entry of an earlier step's list, with `{{file}}`, `{{item}}` and `{{index}}`; saved values become a list, and `{{name.*.var}}` takes one field from each). A request's body is one of `json`, `form`, `multipart` (parts with a value or a file) or `body_file` (one file's bytes); files are referenced and read from disk by the executor, never put in the arguments. Every step's URL is checked against `hosts`, including a URL taken from an earlier answer. Saved values live for one call only; there is no branching beyond `when` (a `command` ability is the way out when a service needs more). Limits: 10 steps, 20 runs per `for_each`. The WordPress manifest is the worked example: the asset's image becomes the post's featured image.
- **Abilities are code; accounts belong to the project** (roadmap 17, decided 2026-10-26). Installing an ability puts its code on the machine and nothing else. Each project adds accounts of it, each with a name and its own keys, as many as it wants: two WordPress sites, two mail accounts, two analytics properties. A channel is an account of an ability that publishes, with a kind and a destination. An ability's keys are never machine-wide or project-wide any more (only KIQR's own keys are); an installed ability has one switch, per project. A call goes through the account it names, else the ability's default; with more than one, tools take a `connection` argument. Stored as `projects/<slug>/connections/<id>/` (yaml committed, `.env` not); the user sees "account". Older homes move once at start. Not yet: reading several analytics properties side by side (a source reads the default account), and machine-wide accounts if several projects ever need to share one.
- **Abilities share accounts and channels through a service** (roadmap 18, decided 2026-10-26). Several abilities often work on one site ("Read posts", "Find posts and reply", "Improve the profile", all on the same login). An account is therefore an account of a *service*, not of one ability: a manifest may name `service` (default: its own id, so nothing changes for one that does not), every ability of that service uses the project's accounts of it, and they agree on its key names. The default, names and lookups are per service; `ability` on the record stays as the one it was made with. Channel kinds carry roles (`does: publish | read | reply | manage`, default `publish`) and a channel has one `publisher` (the user's pick, else the ability it was made with, else the first on), so several abilities act on one channel and exactly one publishes; a call through a channel gets its destination. Coordination is in core, generic for any service: `exclusive` abilities take turns on an account, a hosted program works in the account's own folder (`connections/<id>/data/`, so one browser profile serves every ability of the service), `daily_cap` counts actions per account across abilities (the lowest declared wins), and every action is logged per account (`activity.jsonl`), where a tool's `target` makes the same action on the same thing (a second reply to one post) refused. Conflicting intent stays with the approval cards.
- **kiqr.cloud connects a KIQR agent with third-party apps, and keeps nothing worth stealing** (roadmap 19, decided 2026-10-26). kiqr.cloud (a separate private repo, `~/Projects/kiqr/cloud`: Rails with Devise and Doorkeeper, Postgres, Valkey, Kubernetes like UnblockingAPI) holds accounts (email encrypted, a password hash, no IPs) and finishes sign-ins a plain-http KIQR cannot.

Each agent can be unlinked on its own.
  - **The relay.** A service that only calls back over https (WordPress's "Authorize Application") gets `https://kiqr.cloud/r/<id>`, opened by the agent just before: the browser comes back there once and is sent straight on to the agent's own callback with what the service added. Redis holds the destination for ten minutes; the values are never stored or logged. `connect.rs` uses it for any `callback: https` redirect flow when the agent is signed in, so WordPress connects with nothing pasted.

  - KIQR's own sign-ins live in `signins.rs` (core: kiqr.cloud is KIQR's own service, UnblockingAPI the one service core may name), with tokens in the machine's `.env` (`provider::SIGNIN_KEYS`), refreshed before use. `kiqr signin`, Settings → kiqr.cloud, and the UnblockingAPI ability's Connect tab.

## Pipeline

1. **Crawl** (`kiqr-core::crawl`): sitemap + robots, same-origin BFS, priority for pricing/about/product pages, 200-page cap, tracking params stripped, raw cache written.
2. **Extract** (`abilities/extract-facts`): each page's Markdown → JSON facts with a verbatim quote and confidence, routed to one of twelve sections. Runs during the crawl so facts stream into the UI.
3. **Synthesize** (`abilities/build-profile`): per section, merge facts into fields, resolve conflicts, keep evidence, never touch locked fields. Writes `profile/*.yaml` and `PROFILE.md`, commits.
4. **Brief** (`abilities/business-brief`): one call on top of the sections, the same business profile ContentWriter builds and more. Input: the site URL, every merged section (field name + value) and a numbered page list (path, title, up to three facts). Output: business name, summary, language, geographies, offerings (with source URLs), audiences, tone of voice, brand terms, differentiators, competitors, pricing summary, 3–8 topic clusters and 8–15 content gaps. Clusters come back as page numbers; Rust maps them to URLs (each page in one cluster) and sets `page_count`. Written to `profile/brief.yaml` with a `version` that increments on every write and `source: crawl | edited`, rendered at the top of `PROFILE.md`, committed as `[auto] profile(<slug>): business brief v<N>`. Runs at the end of every synthesis; `POST …/brief` reruns just this step.
5. **Brand** (`kiqr-core::brand`, no model): when fetching ends, before waiting on the model queue, the raw HTML in the cache plus up to three same-origin stylesheets of the home page (5 s, 2 MB each) give the brand: site name and tagline (og/JSON-LD/title), logo (JSON-LD Organization logo, else a logo image in the header), icon (apple-touch-icon, else the largest icon link, else `/favicon.ico`), cover (home og:image), up to 6 colours (theme-color first, then the most used saturated CSS colours, near-duplicates merged), up to 3 fonts ordered by weighted `font-family` use (body/sans stacks count most, monospace and cursive accents least; Google Fonts link order breaks ties), up to 12 images (each page's og:image, then large content images) and one social profile per network. Saved to `profile/brand.yaml`, rendered as a short Brand block in `PROFILE.md`, committed as `[auto] brand(<slug>): …`, emits `brand_updated {logo, colors, images}`. `GET …/brand` builds it from the cache on the fly (without writing) when the file is missing, so projects crawled earlier get one without a rescan; `POST …/brand` rebuilds and saves.
6. **Edit**: the UI and API write sections and the brief; a user edit locks a field, and an edited brief is `source: edited` until the next crawl rewrites it.

Synthesis emits `synthesis_started {total}` (sections to build + 1 for the brief), one `profile_updated {section, by, title, items}` per section and one for `brief`, then `synthesis_finished {sections}` whether it succeeded or not; on failure Seemo says what failed. `page_fetched` carries the page `title` and `words` so the crawl screen can show them.

Chat events are project-scoped and carry the chat id: `chat_created/renamed/deleted`, `chat_turn_started`, `chat_delta` (display only, coalesced), `chat_tool` (started/done/failed with a human label), `chat_message` (a message added or, same id, changed), `chat_turn_finished`, `approval_requested/resolved`; tasks: `task_saved/deleted`, `task_run_started/step/finished`; `config_changed {by, restart}`. None of them go into the crawl log. The web client shares one `EventSource` per URL across listeners.
